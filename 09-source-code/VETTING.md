## What "vetted" means here — two claims, kept apart

**Provenance vetting** (audited tier): each project was selected because its
security posture is externally documented — a published third-party audit,
machine-checked formal verification, or a continuous audit process. That work
was done by the named auditors, not by this repository; the citations live in
each repo directory's `PROVENANCE.md` and in `manifests/audited-code-manifest.json`.

**Content vetting** (every file in this section, both tiers): the bytes on
disk are mechanically scanned for hazards that matter for a read-only text
corpus — trojan-source bidi controls (CVE-2021-42574), invisible codepoints,
credential-shaped strings, private-key material, binary smuggling — and
audited-tier files are re-checksummed against their pinned-commit manifest.

Neither claim is a line-by-line code review by this repository, and nothing
in this corpus is ever executed: consumers read these files as documents.

## Scan parameters (declared, not tuned)

- **nul-bytes / utf8** — binary smuggling — FAIL
- **bidi-controls** — Unicode bidi control set per CVE-2021-42574 (Trojan Source) — FAIL
- **invisible-chars** — zero-width/invisible codepoints — WARN
- **credential tokens** — aws-access-key-id, github-token, gitlab-token, slack-token, google-api-key — FAIL unless provider example
- **private-key-material** — PEM marker followed by base64 body — FAIL; bare marker — WARN
- **pipe-to-shell** — download piped to shell in text — WARN
- **license presence** — each repo directory carries LICENSE/COPYING/PROVENANCE.md

These parameters are external standards (the Unicode bidi control set, the
providers' own documented token prefixes); none was chosen by looking at
what it does to this corpus's results.
